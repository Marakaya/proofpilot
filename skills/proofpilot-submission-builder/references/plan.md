# Plan

Use this workflow when the project needs a testable MVP, experiment, build path, timeline, or demo.

## Process

1. Define the user outcome and the assumption the MVP must test.
2. Choose the thinnest delivery model: manual service, concierge, spreadsheet, no-code workflow, prototype, web app, AI workflow, data notebook, web3 app, or physical pilot.
3. Separate must-have behavior from later features and explicit non-goals.
4. Fit the scope to team skill, time, budget, distribution, compliance, and program constraints.
   For a time-boxed test, size output from the days each activity can actually run, not the total horizon: exclude intake/setup and wrap/analysis days, apply the stated workweek (or state an assumed one), and allow for required review or approval lag. Promise at most the lowest of all simultaneous bounds: hours, per-day or per-person throughput, available participants or data, and reviewer capacity. A fitting hours total does not prove the schedule fits. Overlap phases only when stated capacity supports both on the same day, and say so. State the binding constraint; if the goal exceeds it, cut scope or extend the timeline.
5. Identify dependencies, credentials, external services, data, security work, and fallback paths.
6. Add instrumentation that can prove whether the MVP worked.
   For product-market fit, measure first value, repeated meaningful use, payment, or renewal as appropriate to the stage. For AI, validate accepted outcomes and full delivery costs before promising autonomy or unit economics; use the focused PMF and AI references.
   For an experiment, define actions for success, measured threshold failure, and insufficient valid data. Continue only when every stated success criterion and prerequisite passes. Name the unmet condition, including problem recurrence or ongoing service cost/time when tested; a measured miss is not missing evidence. One explicit stop/revise fallback can cover remaining threshold failures without listing every combination. Keep any revision or evidence-gathering step within the user's available time and budget.
7. Produce a demo script that shows the promised outcome rather than a feature tour.

## Required Output

- MVP promise and target user
- assumption being tested
- delivery model and rationale
- must-have scope and non-goals
- milestone sequence with owner and acceptance condition
- cost, credentials, and dependencies
- risks and fallback paths
- measurement plan
- demo script

Do not recommend blockchain, AI, custom software, or automation unless it is necessary for the test or materially improves the chosen outcome.
